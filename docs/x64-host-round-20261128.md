## What the counts said about register copies

The plan was "9 % of the instructions are register copies: shifts need the count in rcx, and the allocator does not commute".
Counted as executed, not as written:

- register copies are 12 % of mcc's executed instructions when mcc builds it and 14 % when clang does: no gap;
- a count copied to rcx before a shift: 280 of 48 600 copies as written, 0.01 % as executed (the "3600 into rcx" are the
  fourth argument of calls);
- what mcc ran more of than clang: stack loads and stores (11.6 % against 7.6 %, push and pop counted), widenings of 32-bit
  values (`mov %r15d,%eax`, `movzbl` after `setcc`: 1.9 %), copies followed by a two-address operation (2 % against 1.2 %);
- callee-saved saves and restores are 5 % of the instructions on both sides (mov against push / pop).

## Found, not done

- **interp and the block layout.** The same interp function placed 16, 32, 48 bytes further on runs in 54 to 67 ms: more
  than the 10 % put down to the layout. It is not the tree of compares: with a jump table (below) the same function runs in
  51 or in 65 ms by where it is placed. The machine is a Skylake-family Xeon, where a jump that crosses or ends on a
  32-byte boundary is not kept in the decoded-instruction cache (the JCC erratum; gas has -mbranches-within-32B-boundaries
  for it). Times of small loops full of jumps on such a machine say little about the layout; a Zen does not have this.
- **Shrink wrapping.** root_of, fold, live_add, read_end save six registers to return at once on their usual path. It needs the
  parameter kept in its own register up to the first call (a split of its range at the way into the part with calls).
- **Spills in loops with calls** (uses_beyond, carve_one, split_loops): more values live across the calls than the six
  callee-saved registers; whole ranges go to memory. Reloads other than the one above: 3.7 % of the instructions.
- **32-bit parameters and results** widened on every use as an index (ir_resolve: 1.3 %): the ABI leaves the upper half
  open. A static function's results could be known clean from its returns.
- `movswl` then `movslq` of one load, a constant loaded inside a loop for a cmov, `test` twice for two cmovs on one condition,
  `bt` for a bit test: seen in struct_test and lowest_bit, each under 0.3 % of mcc's own instructions.

## mcuda on x86-64 (the translator, cuda/jitx64.c)

Measured with two kernels of 2^20 floats, 64 blocks of 256 threads, grid-stride loops, one host thread (MCUDA_THREADS=1):
hist (`atomicAdd(&bins[lrintf(x * 255) & 255], 1)`) and fmap (`expf(x) / (1 + x) + floorf(x * 8)`), four launches each.

| | hist | fmap |
|---|---|---|
| before (the translated code left for the interpreter 21 M times: cvt 8.4 M, atom 4.2 M, call of a built-in 4.2 M, div 4.2 M) | 225 ms | 326 ms |
| cvt, fgen, atom, fdiv and built-in calls in the translated code (calls of the interpreter's functions) | 194 | 289 |
| mc_tbits a table (it searched the type table for every conversion and atomic: 20 % of the time), atomics by compare-and-swap, no mutex | 100 | 250 |
| float to int by cvtss2si / cvttss2si, to an integral float by roundss (what does not fit, and NaNs, leave for the interpreter) | 50 | 165 |
| integer atomic add / exchange / compare-and-swap by lock xadd / xchg / lock cmpxchg | 33 | 166 |

Translated code leaves 0.13 M times now (each thread's return). tests/cuda/jitedge holds the translated code to the
interpreter's bits at the values where the processor and PTX part. It found the interpreter itself differing between x86-64
and arm64: lround / lrint of what no long holds were a C cast (0x8000000000000000 on one, the nearest long on the other).

Found, not done:
- hist with four host threads takes 95 ms, three times the one thread's 33: the 256 bins are 16 cache lines that four
  processors write in turn. A device does not pay for that; mcuda could only by giving each host thread bins of its own.
- The same kernel with each thread on a contiguous part (histc) takes the same time as the strided one, at 4 MB and now that
  the loop's own work is small: threads run one after the other did not cost here what was expected of them.
- What is left of fmap is the C library's exp and the marshalling of a built-in call's arguments (arg_bits, 14 %).
- Calls and returns of device functions still leave (29 k and 140 k in the tests).
